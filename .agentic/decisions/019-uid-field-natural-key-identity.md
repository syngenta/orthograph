# ADR-019: `__uid_field__` — Natural-Key Identity Semantics and Hardening

**Date:** 2026-06-15
**Status:** Accepted
**Category:** graph definition / domain model / identifier safety

---

## Context

`NodeModel` supports an optional `__uid_field__` class variable that names the
property acting as a node's unique identifier:

```python
class City(NodeModel):
    __label__ = "City"
    __uid_field__ = "name"
    name: str
    country: str
```

The field drives four distinct subsystems:

| Subsystem | Behaviour when `__uid_field__` is set |
|-----------|--------------------------------------|
| `CypherGenerator.merge_node` / `merge_query` | emits `MERGE (n:City {name: $name})` — idempotent upsert |
| `CypherGenerator.generate_constraints` | emits `CREATE CONSTRAINT … REQUIRE n.name IS UNIQUE` |
| `CypherGenerator._rel_query` | resolves endpoint anchor: `MATCH (a:City {name: $src_uid})` |
| `GraphValidator._validate_and_index_nodes` | builds `node_index` keyed on UID values for referential-integrity and cardinality checks |

A code review against the current implementation identified three gaps:

### Gap 1 — No definition-time validation of the declared field name

`__uid_field__` is a plain string. A typo (`"naem"`) is not caught at class
definition time. The error surfaces later, deep inside `CypherGenerator._params_model`
or `_require_uid`, as an opaque `CypherUnknownPropertyError` or `KeyError` far from
the actual mistake. `NodeModel.__init_subclass__` already validates that `__label__`
is present; `__uid_field__` receives no comparable guard.

### Gap 2 — No rejection of nullable UID fields

A field declared as `name: str | None` resolves to `TypeInfo(is_required=False)`.
A UID that can be `None` means some nodes of this type are unaddressable:
`MERGE (n:City {name: null})` matches all nodes with no name, and a `UNIQUE` constraint
on a nullable field has no teeth in Neo4j/Memgraph (null is not indexed as a
distinct value). The library currently accepts this silently.

### Gap 3 — Phantom-key fallback in `CypherGenerator._rel_query`

When a node type used as a relationship endpoint has no `__uid_field__`, the
generator silently substitutes the literal string `"uid"`:

```python
# src/orthograph/cypher/generator.py:195-196
src_uid_field = src_node_type.__uid_field__ or "uid"
tgt_uid_field = tgt_node_type.__uid_field__ or "uid"
```

This fabricates a property key the model never declared. The identifier passes
the grammar guard (`validate_identifier` — ADR-008) but **bypasses the model guard**
(`_check_model_properties`), because endpoint resolution happens outside the
property-check path. The generated Cypher silently matches zero nodes whenever the
endpoint node type has no `uid` property. No error is raised; data is silently lost.

---

## Decisions

### Decision 1 — Natural-key only: `__uid_field__` must name a declared property

> `__uid_field__` is a pointer into the model's declared property map, not a free
> string. The only supported identity strategy is a **natural key**: a domain-meaningful
> property that already appears in `get_property_specs()`.

**Rejected alternatives:**

- **`auto` / synthetic ids.** A value generated by the database or the library
  (`elementId`, UUID) is not a declared property and does not appear in
  `get_property_specs()`. It cannot participate in the declared/observed mirror
  (ADR-015): it has no declared face the comparison engine can address. It makes
  `generate_constraints` impossible (no property to constrain), breaks `merge_node`
  (no field to MERGE on), and hides node identity from the schema. Rejected on
  mirror-principle grounds.

- **Direct/provided id outside the model.** An id supplied by the caller but not
  declared as a typed property is equivalent to `auto` from the library's perspective
  — the model cannot see it, validate it, or constrain it. Rejected for the same
  reason. If an application needs a surrogate key, declare it as a typed property
  (`uid: str`) and point `__uid_field__` at it; the identity is then visible to the
  model.

- **Composite natural keys.** `__uid_field__` as a single string cannot express
  `(name, country)` identity. Composite keys are not supported in this decision.
  If/when composite identity is needed, the correct evolution is a typed `Uid`
  value object (see *Future* section below), not a sentinel string or a list.

### Decision 2 — `__uid_field__` is validated at class-definition time

`NodeModel.__init_subclass__` must check, whenever `__uid_field__` is set in
`cls.__dict__`, that:

1. The named field exists in `cls.get_property_specs()`. Failure raises
   `MissingClassVarError` with a message naming the class and the missing field.

2. The named field is not nullable — its `TypeInfo.is_required` must be `True`.
   Failure raises `MissingClassVarError` with a message explaining that a UID
   field must be a required (non-optional) property.

These checks run at import time, not at first use. The error is as close to the
mistake as possible.

**Why `MissingClassVarError` and not a new exception type?**
The existing `MissingClassVarError` semantics cover both cases: the field is
either absent from the model (case 1) or present but in an inadmissible form
(case 2). Introducing a new exception type would complicate `except` clauses for
callers that already catch `MissingClassVarError` from `__label__` validation.
Both errors are programming errors in the class definition.

### Decision 3 — No implicit UID fallback in relationship endpoint resolution

The `or "uid"` fallback in `CypherGenerator._rel_query` is eliminated.
A node type used as a relationship endpoint with no `__uid_field__` must raise
`MissingUidFieldError` — the same exception already raised by `_require_uid` for
`merge_query` and `delete_by_uid_query`. The error message must name the
relationship label and the endpoint (source or target) that lacks a UID field.

This makes the `or "uid"` pattern illegal at the call site and turns a silent
data-loss bug into a loud, actionable error.

---

## Consequences

### Positive

- **Typos in `__uid_field__` are caught at import time**, at the class definition,
  not buried in a generator or validator call stack. The experience for a developer
  is: `import my_schema` → `MissingClassVarError: City.__uid_field__ = 'naem' is not
  a declared property`.

- **Nullable UIDs are rejected before they reach the database**, preventing silent
  constraint erosion and MERGE ambiguity.

- **Silent phantom-key queries are eliminated.** A schema author who forgets to
  declare `__uid_field__` on an endpoint node type gets an explicit error the first
  time they call any relationship generator, not a query that silently matches nothing.

- **ADR-008 model guard is now complete for endpoint resolution.** The phantom-key
  fallback was the last site where an undeclared property key could reach the Cypher
  generator unchecked.

### Negative / risks

- **Breaking for callers who omit `__uid_field__` on relationship endpoints and
  rely on the `"uid"` fallback.** Any schema that happens to have a property named
  `uid` and no explicit `__uid_field__` declaration will break at the `_rel_query`
  call site. Mitigation: the fix is mechanical — add `__uid_field__ = "uid"` to the
  affected node types. The error message names the relationship and the endpoint.

- **Breaking for callers who declare `__uid_field__` pointing at a nullable field.**
  These schemas are broken today (MERGE and constraint semantics are wrong); the
  new check surfaces the existing bug rather than creating a new one.

## Future: Typed `Uid` value object

If composite identity is ever needed, the correct evolution is:

```python
class City(NodeModel):
    __label__ = "City"
    __uid__ = Uid("name", "country")   # typed, validated, composite-capable
    name: str
    country: str
```

A `Uid` object can validate its field names against the property specs at
class-definition time, carry a strategy, and express composite keys — without
adding magic strings to `__uid_field__`. Under that design `__uid_field__` is
retired in favour of `__uid__`, and `Uid("name")` is the single-field degenerate
case. This is explicitly **deferred** and must not be implemented before a concrete
use case requires it.
